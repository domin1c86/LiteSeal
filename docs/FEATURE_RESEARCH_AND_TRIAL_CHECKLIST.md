# WhatsApp / Telegram 功能调研与 LiteSeal 试做清单

调研日期：2026-09-22。LiteSeal 代码基线：`7dd2bde`。目标平台：Windows；面向 5–10 人熟人内测，先形成稳定、方便的日常单聊，再扩展多人协作。

**建议首先试做：通知与静音 → 本地消息搜索 → 加密图片/文件。** 三项分别解决漏消息、找不到历史、必须切换软件传文件的问题。已有文字聊天可靠性验收仍是内测门槛，可以与功能开发分开推进，但不能因新功能完成而自动关闭。

本文是调研和后续实施建议，不表示功能已经开发或通过测试。只采用官方产品页、帮助中心、博客和开发文档；不把传闻、第三方客户端或测试版功能当成普遍可用功能。功能可能受客户端、地区、订阅和分批发布影响，涉及上线前应再次核对。本文覆盖对 LiteSeal 有参考价值的主要能力，不声称穷举两款产品的全部功能。

### 对 LiteSeal 最重要的三个差异

1. **默认端到端加密与云端便利性不能混为一谈。** Telegram 的云聊天搜索/同步体验可作为产品目标，但不能直接作为 LiteSeal 的服务端明文存储方案。WhatsApp 的私人聊天加密描述也不能直接推广到所有频道、商业或 AI 场景。依据：[Telegram 加密说明](https://telegram.org/faq#q-how-do-you-encrypt-data)、[WhatsApp 隐私问答](https://www.whatsapp.com/privacyquestions)。
2. **相同图标未必代表相同状态。** LiteSeal 当前 `delivered` 是收件设备持久化确认，本机未读清零也不等于对方收到阅读回执；不要仅模仿勾号颜色。依据：[WhatsApp 回执说明](https://faq.whatsapp.com/665923838265756/?cms_platform=iphone&locale=te_IN)、[Telegram FAQ](https://telegram.org/faq#q-what-do-the-check-marks-mean)。
3. **多设备是密钥与数据生命周期工程。** 当前单设备内测不应为了增加登录入口而解除限制。恢复历史、吊销设备、离线消息和联系人身份变更需要一起设计；这是结合 LiteSeal 源码作出的实施判断。

## 3. 可以直接排进开发队列的清单

优先级沿用仓库：P0 为内测门槛，P1 为日常 Windows 体验，P2 为扩展能力，P3 为需额外产品需求的方向。规模是实现相对复杂度：S 为主要本机改动，M 为多层联动，L 为新服务/协议能力，XL 为需先做架构验证；不是工期承诺。所有复选框表示待完成的验收切片。

### 3.1 P0：已有基础的试用门槛

- [ ] **T00：文字聊天与安装验收**（W-01～W-10，规模 M）：用隔离账号/数据库完成双 Windows 安装、注册、互加、指纹核对、双向中文/emoji、断网重试、离线补收、重启历史、退出再登录；加入 ACK 丢失、乱序和编辑/撤回晚到场景。完成标准为每个场景有环境、步骤、结果及失败记录，不能以“编译通过”关闭。当前文档任务不执行这些交互测试。
- [ ] **T01：状态含义与数据边界确认**（W-06/W-07、S-01，规模 S）：核对待发送、服务端保存、设备送达、失败的文字；解释单设备限制、密钥丢失、本机删除/撤回的效果。完成标准为 UI、错误提示和使用文档一致，未实现对方已读时不显示“对方已读”。

## 4. 首批三项如何落地

### T02：通知与静音

- **用户流程**：收到后台消息 → 显示“有新消息” → 点击进入对应会话；会话菜单可静音；托盘菜单明确“打开/退出”。首次收起到托盘时说明程序继续运行。
- **实现切片**：先加账号/会话通知偏好及业务命令；再在 Electron 主进程创建通知、维护托盘和退出生命周期；最后接 UI 设置和通知点击路由。默认不传正文到系统通知中心。
- **改动范围**：`electron/main.ts`、`electron/contracts.ts`、`electron/preload.ts`；`desktop/src/commands/`；`core/src/db/`；`ui/src/components/ContactList.tsx` 与设置界面。具体命令名实施时再定，不增加任意 shell/文件系统桥接。
- **边界**：用账号与消息 ID 去重，离线积压按会话合并提醒；归档并不自动静音。退出账号、应用锁定和消息撤回时清理相关通知。静音只控制提醒，不阻断消息落库和 ACK。
- **验收数据**：两账号、一个静音会话、前台/后台/锁屏、100 条离线补收、通知后账号切换、点击后原消息已撤回。记录提醒次数和最终跳转，不能只验证通知对象被创建。

### T03：本地搜索

- **用户流程**：Ctrl+F 输入关键字 → 显示已搜索范围与进度 → 选中结果 → 加载该消息周边历史并高亮。先支持单会话，再考虑全局。
- **首版方案**：复用本地密文读取与解密，分批扫描并在内存匹配；先采用明确的子串规则，支持中文/英文大小写处理。不为了全文索引把正文写到未加密的持久化表。
- **关键依赖**：现有正文解码和编辑/撤回、本机删除投影必须成为搜索与显示共同使用的规则。增加“按消息 ID 读取上下文”的业务接口，不能只搜索当前已加载的 50 条。
- **改动范围**：`core/src/db/repository.rs`、`desktop/src/commands/chat.rs`、`electron/contracts.ts`、`ui/src/components/Chat.tsx`、`ui/src/lib/messageContent.ts` 与消息投影逻辑。批处理和取消应避免长时间持有 SQLite 同步锁。
- **验收数据**：单会话 10,000 条、中文/emoji/长文本、编辑后旧词、撤回/删除、损坏密文、快速切换账号及取消搜索。首轮测量首批结果耗时和内存峰值，再确定正式性能门槛；跳过的无法解密记录须可见。
- **保留边界**：引用/转发本身是独立快照。原文撤回后，原文搜索结果消失，但其他消息中仍存在的合法快照按现有规则处理，不能误承诺全局抹除所有副本。

### T04/T05：加密文件与图片

- **用户流程**：选文件 → 看到名称/大小并确认 → 进度 → 发出附件消息；对方验证并下载 → 安全预览或另存为。单文件先跑通，批量与大文件断点续传随后增加。
- **数据设计**：使用经过审查的认证加密方案与每附件随机密钥。聊天加密正文携带附件描述、对象标识、密钥/nonce 等解密材料及完整性绑定；服务端存储密文、授权和最少必要元数据。私钥及附件密钥由 Rust 管理，不进入日志或新增 JS 密钥接口。
- **传输设计**：先完成受保护的上传/下载接口、大小限制、配额与孤立对象回收；再把上传完成的对象绑定到已签名消息。下载鉴权不能只依赖“知道 URL”。第一版允许失败后重传整个小文件，但继续同一任务，避免重复聊天消息。
- **本地文件边界**：主进程提供受限选取/保存能力，不接收渲染进程任意路径读写请求；清理临时文件；名称规范化防路径穿越；默认不自动打开可执行内容。缩略图同样受加密与缓存策略保护。
- **兼容与顺序**：`ui/src/lib/messageContent.ts` 当前是文字/引用/转发结构，附件应有版本和未知类型占位；服务端、Rust、桌面契约与 UI 同步升级。若新增外层信封字段，须一起更新 `signing_bytes()`、中继校验和协议用例，不能只改界面 JSON。
- **回收规则**：发送失败与取消产生的孤立对象按可配置期限清理；已发送对象的保留期限、用户配额、删除权限以及过期后是否可重下在接口实现前写清。附件消息持久化 ACK 与文件已下载是两个状态。
- **验收数据**：20 MiB 边界、空文件、文件伪装、超长名称、跨账号 URL、密文篡改、上传成功但消息发送失败、下载中断、磁盘满、缓存清理后重下、离线用户稍后下载。观察上传流量、对象占用和失败率。

## 5. 建议推进顺序与试用判据

| 阶段 | 工作内容 | 进入下一阶段的依据 |
| --- | --- | --- |
| A：可靠文字基线 | T00/T01，补齐已有 D-01～D-03 验收；新功能可在隔离环境开发 | 无未解决的消息丢失、越权或身份混淆；双 Windows 场景记录齐全 |
| B：高频日常缺口 | T02 → T03 → T04/T05；穿插 T06/T07/T09 | 用户能接到提醒、找旧消息、发图片文件；失败流程可恢复 |
| C：完整内测体验 | T08、T12～T15；按反馈选 T10/T11/T16 | 内测支持范围、拉黑/账号/更新边界清晰；缓存与通知无正文泄漏 |
| D：需求驱动扩展 | 在 T17～T26 中按需求选择一条主线 | 有需求证据，且前置技术验证与安全边界通过，不同时承诺群聊、多设备和音视频 |

建议先由开发者两机验证，再让 2 位用户试用 24 小时，稳定后扩展到 5–10 人观察 72 小时。这是试用方案，不是本次已经取得的结果，也不是对开发工期的估算。发放安装包和外部部署仍按仓库约定另行确认。

试用记录只收集用户主动提供的反馈及必要诊断，不自动收集聊天正文：

- **可靠性**：发送失败是否能解释和恢复；是否发生消息丢失、重复展示或跨账号数据混入。出现任一数据/权限阻断问题时先修复。
- **通知价值**：是否减少漏看消息；是否出现重复、误跳转或静音失效。
- **搜索价值**：能否找到早于当前分页的记录；搜索进度是否可理解；记录设备、数据量和耗时。
- **附件价值**：是否减少切换其他软件；失败重试是否成功；记录文件大小区间、带宽/存储使用，不记录正文。
- **下一步需求**：语音、小群、多设备哪个确实被反复需要；按反馈选择下一阶段，避免按竞品功能数量追进度。
