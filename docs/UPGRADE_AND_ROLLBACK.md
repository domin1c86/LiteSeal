# Windows 升级与回滚

状态：升级入口与操作脚本已编写，尚未在干净 Windows 上执行安装/升级/回滚验收。没有发布安装包或部署服务。

## 签名打包

内测仍可运行 `npm run dist:win`。正式包须提供发布证书，将 `LITESEAL_SIGNED_RELEASE=1`，通过受保护环境注入 `CSC_LINK` 和 `CSC_KEY_PASSWORD` 后运行同一命令。启用 `forceCodeSigning`，签名失败必须终止；禁止提交证书、密码或日志中的凭据。使用受信任时间戳服务，由证书持有人维护续期和撤销流程。

打包后对安装 EXE、应用 EXE 和 Rust sidecar 分别运行 `Get-AuthenticodeSignature`，记录签名状态、签发者和文件 SHA256；如 sidecar 未被打包工具签名，发布者必须先用其证书签名该二进制再重新打包。三个签名均有效才可提交人工发布。版本检查只读取固定仓库的正式 Release，不自动下载或执行软件。

## 升级前

1. 保留原安装包及其版本、SHA256、签名信息。完全退出托盘和开发进程。
2. 执行 `powershell -NoProfile -File scripts/backup-before-upgrade.ps1 -Destination <新的快照目录>`。脚本复制原 Windows 用户下的应用数据与密钥目录，并逐文件核对 SHA256；不修改原目录。
3. 快照包含敏感身份数据，保留在受保护本地存储。Windows DPAPI 密钥不能据此直接换机或换 Windows 用户。
4. 核对新包签名和发布者提供的 SHA256，然后手动运行 NSIS 安装，保留原数据目录。前后端需一起升级，新端点不兼容旧服务端。

## 验收记录

记录 OS、旧/新版本、原库副本、安装退出码、身份指纹、历史数量、加密草稿、备注/列表、待发附件与未读状态。验证登录、中文消息、文件下载和旧消息搜索。记录崩溃、磁盘不足、安装被中断和服务端版本不匹配的实际表现，不能仅用构建成功关闭 T15。

## 回滚

完全退出应用。先将失败升级后的数据复制到另一个独立目录；保留新产生的消息证据。安装经过核验的旧版本，并在原 Windows 用户下恢复与旧版本配套的升级前快照，逐文件核对 manifest。不要把旧程序直接指向已经迁移的新库，也不要混用不同时间的数据库与密钥。

回滚恢复快照会失去快照之后的本机状态；远端已 ACK 的密文不保证能重新下载，因此发布前必须用隔离账号演练这个边界。暂不提供自动覆盖数据的恢复按钮。
