# T23 两台 Windows 可信设备：设计交付

2026-09-30：设计稿，本轮没有开放第二设备登录、增加服务端接口或执行迁移。现有单设备限制继续生效，T22 离线档案不代替设备授权。

## 首个切片与身份

每账号最多两台 Windows，支持原设备在线授权、独立设备密钥、单聊新消息、用户选定的单聊历史迁移和第二设备撤销。原设备保留群能力；第二设备明确显示“群聊仅原设备可用”。现有群按账号绑定单设备，群多设备需另做成员/设备阶段及收件集合设计。

原设备已被联系人钉住的 Ed25519 公钥作为首版账号授权根。对应私钥仅留原设备；第二设备生成独立加密/签名密钥，不能复制原设备私钥。首版不允许第二设备替换/撤销授权根，不提供根轮换或凭密码/管理员重置恢复根。

授权域 `LiteSeal/device-grant/v1` 绑定服务器 origin、账号、设备编号、两组公钥、挑战、到期、单调版本和前序哈希。撤销延续同一链。客户端从原已信任根验链，服务器返回的公钥本身不是信任锚。

## 加入与撤销

1. 第二设备用账号密码申请加入意向并签署一次性挑战；申请会话不能读消息/历史。每账号最多一个有效意向，有效期 10 分钟。
2. 原设备显示第二设备两组指纹，用户通过可信渠道核对。原设备向新加密公钥发送随机认证挑战，新设备解密后以新签名私钥证明收到，绑定服务器/账号/意向，拒绝跨设备重放。
3. 原设备验签并签发授权。服务端事务锁账号，核对有效原会话、根签名、挑战、版本、上限和新设备签名，原子保存事件/设备并授予新会话正常权限。
4. 响应丢失时查询或重试原意向/授权编号和签名内容，不自动创建新身份。

撤销由原设备确认并签署；服务端同一事务撤销目标 HTTP/WS/刷新会话、队列和后续资格，并关闭现有 WS。离线撤销后重新上线不能补收后续消息。已经下载的历史不能远程擦除。

## 接口与数据流

拟新增 `/devices/join_requests`（申请/查询/取消）、`/devices/grants`（授权）、`/devices/revoke`（撤销）、`/users/:id/device_manifest`（可验证版本链）。页面仅传类型化业务操作，不能提交私钥或任意签名事件。PostgreSQL 增加意向、事件和授权版本；SQLite 增加 origin/账号/设备隔离与信任链。迁移保留原库和根指纹，失败保持原单设备状态。

多设备单聊采用协商后的新信封版本，绑定发送设备证书、收件授权版本与完整设备集合，每设备一份密文，服务端整个批次原子接受或拒绝。加入/撤销与提交按授权版本协调。未知结果仅查询/重试原批次；明确未接受且版本过期时，才允许显式重建。客户端验根授权、设备签名、链并落库后 ACK，各设备游标独立。

历史迁移由原设备按用户选定会话/时间范围创建认证加密流，绑定两设备、授权版本、范围、顺序及到期；中继只存密文。新设备不用原私钥，解密后以自己的本机身份重加密。保留原消息/变更证据，但正文是受信原设备迁移，标记 `authorized_history_transfer`，不能伪称新设备收到的原始 `verified_v2`。删除/撤回/附件授权规则继续生效。

新设备默认无旧历史，不迁移待发、定时、上传、ACK；草稿/静音/定时任务各自独立。旧消息编辑/撤回仍仅原发送设备按现有时限执行。旧客户端不支持新授权链/信封时禁止开启多设备；未开启账号继续原单设备协议，密码登录不得成为隐式设备替换。

## 实现前门槛

两台 Windows 验证：两组公私钥证明、指纹核对、响应丢失、重放/过期、并发加入/撤销、错误根、授权链乱序/篡改、设备上限、旧客户端拒绝、撤销旧 HTTP/WS/refresh、离线撤销、新旧历史隔离、迁移中断/损坏和原发送设备编辑权限。

独立审查重点为授权根长期持有、设备目录回滚、收件集合/事务竞争，以及迁移正文与原证据的信任差异。审查和可运行验证通过前，不开放普通用户多设备登录。失去原设备但持有 T22 备份时只能离线阅读；在线根恢复必须另行设计。
