# T23 两台 Windows 可信设备：设计与授权基础

## 2026-10-02 服务端授权控制流程

新增 PostgreSQL 迁移 15，保存钉住的根、签名事件、加入申请和独立授权设备投影；原历史迁移、`devices`、普通会话及 V2 单聊协议没有转换。设置 `LITESEAL_DEVICE_AUTHORIZATION_ORIGIN` 为服务器公开规范 origin 后启用控制流程，默认关闭；配置与已保存根的 origin 不一致时拒绝验链，不静默换根。

已接通 `/devices/join_requests`（密码验证、列表）、`/:id`（状态/取消）、`/:id/intent`、`/:id/challenge`、`/:id/proof`、`/devices/grants`、`/devices/revoke` 和 `/users/:id/device_manifest`。申请凭据只能操作自己的申请，不能访问账号会话、设备、消息、群或目录。服务器只保存其哈希；Rust 请求体不实现 Debug，不记录口令或原凭据。申请绑定密码状态，修改密码使旧未完成申请失效。

服务器事务按账号→原设备→会话锁顺序核对根与会话、一次性服务器挑战、完整申请/挑战/证明、期限及授权版本。每账号最多一个有效申请；原申请编号/凭据/公钥重试返回相同设备编号和挑战，不延长期限。取消与授权互斥，迟到意向/证明不能重新提交；取消重试可查询原取消状态。授权/撤销同编号同内容幂等，旧授权重试不会使已撤销设备复活。

每账号最多 4096 条申请及 4096 个签名事件，完整请求/事件最多 16 KiB；目录每页最多 100 项/512 KiB，提供分页版本与当前头。分页内容仍必须由客户端从独立可信根验链，不能信任服务端返回的状态或头。目录/投影损坏时读写均明确失败，不重写旧证据。

本切片返回 `messaging_enabled=false`：授权设备未加入普通 `devices` 表、不创建访问/刷新会话、不能登录或收发单聊。后续在完整设备收件集合协议、客户端和审查门槛落实后再激活；本次控制流程不是完整多设备上线。

30/30 专用 PostgreSQL 用例实际通过（0 失败/跳过），其中新增 6 项真实 HTTP 授权流程、取消竞争、并发申请、篡改/越权、密码/期限/目录损坏及默认关闭测试。报告 `database-2026-10-01T19-45-11-117Z.json`；每项独立运行，仅合成身份和新随机标记库，不使用业务数据。下一步 Rust 客户端接口与分页验链同步。

## 2026-10-02 持久化验链增量

`core/src/trusted_devices.rs` 增量创建授权根/日志表，不改历史迁移；按规范 origin/账号隔离，只保存公钥、签名及公开证明。根必须由调用者独立钉住，已有根不得静默替换。SQLite 一致读事务回放每项签名/版本，并核对持久头；写入使用 immediate 事务、调用者已知头和整批原子提交。每批最多 100 项/512 KiB，单事件最多 16 KiB；实时入队校验当前期限，已接受历史回放校验签名时的期限。

外部已信任 `Checkpoint` 可以拒绝截断、回滚和分叉；整份数据库及其高水位同时回滚且调用者没有外部可信高水位时，无法单凭数据库判断新鲜度。后续设备目录/平台安全存储必须继续解决该边界，不能把本次头一致性检查称为完整防回滚。

6 项 SQLite 测试通过：关闭重开重新验链、撤销后原授权重试不复活、批量失败回滚、实时过期与历史回放区分、两连接同时写入只有一项成功、错根/账号/服务器、已知高水位回滚、签名/头损坏及批次数量限制。`trusted-devices-2026-10-01T19-31-15-151Z.json` 为 passed，包含 9 项共享协议、6 项持久化测试和离线示例。普通应用尚未调用这一目录模块；服务端授权、目录读取、信封及桌面流程继续实现。

## 2026-10-02 授权原语与可运行验证

`shared/src/trusted_device.rs` 已实现独立加密/签名密钥加入意向、原设备签名的加密随机挑战、第二设备解密及签名证明、授权/撤销和完整验链。`cargo run --locked -p liteseal-shared --example trusted_device_trial` 使用两个临时 Rust 身份离线执行授权、原编号重试和撤销；`npm run test:devices:trial` 将实际短测写入 `target/test-results/trusted-devices-*.json`。原有正常登录和单设备限制保持现有行为，服务端和桌面授权流程尚待实现。

- 根锚包含规范 HTTP(S) origin、账号、原设备编号及两组公钥；签名输入拒绝非规范 origin、路径、凭据、查询和片段。根须从已经核对的联系人身份取得，不能直接信任服务器目录。
- 加入意向由第二设备签名，绑定根锚、独立公钥、服务器 32 字节随机挑战及最多 10 分钟有效期。服务器后续必须事务保存并核对一次性意向和挑战；共享验签不能替代服务器状态。
- 原设备签名的加密挑战绑定完整意向摘要、下一版本、前序哈希及期限。第二设备必须解密出随机 nonce，再签名提交 nonce 与挑战摘要；对公开 nonce 摘要签名不构成加密私钥持有证明。nonce 在证明发布后为公开材料，私钥从不输出。
- 授权事件绑定全部证明，撤销绑定被撤设备和原授权哈希。状态只从钉住的根及已验签事件重建，不允许反序列化服务器提供的状态。最多两台设备，撤销后设备编号和公钥不再复用；只有原根可授权或撤销。
- 同编号同字节重试幂等；已撤销后重试旧授权返回既有链状态，不恢复设备。相同编号异内容、并发版本、错根、过期实时提交和证明移植均拒绝。历史回放按当时已签名时间验链，不因当前时间超过意向期限而丢弃已接受授权。
- 每根链最多 4096 个事件，避免无界目录回放；达到上限拒绝新事件。本切片不解决整份本机数据回滚，需要后续持久高水位、目录协议和独立审查。

9 项授权测试及离线示例通过，shared 全部 59 项测试、格式和 shared/all-targets Clippy 通过。保留既有 LNK4098 链接警告。下一步持久化验链，再接入受限意向/授权/撤销事务、单聊多设备信封和桌面；未交付这些部分前不将 T23 认定完整可用。

## 首个切片与身份

每账号最多两台 Windows，支持原设备在线授权、独立设备密钥、单聊新消息、用户选定的单聊历史迁移和第二设备撤销。原设备保留群能力；第二设备明确显示“群聊仅原设备可用”。现有群按账号绑定单设备，群多设备需另做成员/设备阶段及收件集合设计。

原设备已被联系人钉住的 Ed25519 公钥作为首版账号授权根。对应私钥仅留原设备；第二设备生成独立加密/签名密钥，不能复制原设备私钥。首版不允许第二设备替换/撤销授权根，不提供根轮换或凭密码/管理员重置恢复根。

授权域 `LiteSeal/device-grant/v1` 绑定服务器 origin、账号、设备编号、两组公钥、挑战、到期、单调版本和前序哈希。撤销延续同一链。客户端从原已信任根验链，服务器返回的公钥本身不是信任锚。

## 加入与撤销

1. 第二设备用账号密码申请加入意向并签署一次性挑战；申请会话不能读消息/历史。每账号最多一个有效意向，有效期 10 分钟。
2. 原设备显示第二设备两组指纹，用户通过可信渠道核对。原设备向新加密公钥发送随机认证挑战，新设备解密后以新签名私钥证明收到，绑定服务器/账号/意向，拒绝跨设备重放。
3. 原设备验签并签发授权。服务端事务锁账号，核对有效原会话、根签名、挑战、版本、上限和新设备签名，原子保存事件/设备并授予新会话正常权限。
4. 响应丢失时查询或重试原意向/授权编号和签名内容，不自动创建新身份。

撤销由原设备确认并签署；服务端同一事务撤销目标 HTTP/WS/刷新会话、队列和后续资格，并关闭现有 WS。离线撤销后重新上线不能补收后续消息。已经下载的历史不能远程擦除。

## 接口与数据流

拟新增 `/devices/join_requests`（申请/查询/取消）、`/devices/grants`（授权）、`/devices/revoke`（撤销）、`/users/:id/device_manifest`（可验证版本链）。页面仅传类型化业务操作，不能提交私钥或任意签名事件。PostgreSQL 增加意向、事件和授权版本；SQLite 增加 origin/账号/设备隔离与信任链。迁移保留原库和根指纹，失败保持原单设备状态。

多设备单聊采用协商后的新信封版本，绑定发送设备证书、收件授权版本与完整设备集合，每设备一份密文，服务端整个批次原子接受或拒绝。加入/撤销与提交按授权版本协调。未知结果仅查询/重试原批次；明确未接受且版本过期时，才允许显式重建。客户端验根授权、设备签名、链并落库后 ACK，各设备游标独立。

历史迁移由原设备按用户选定会话/时间范围创建认证加密流，绑定两设备、授权版本、范围、顺序及到期；中继只存密文。新设备不用原私钥，解密后以自己的本机身份重加密。保留原消息/变更证据，但正文是受信原设备迁移，标记 `authorized_history_transfer`，不能伪称新设备收到的原始 `verified_v2`。删除/撤回/附件授权规则继续生效。

新设备默认无旧历史，不迁移待发、定时、上传、ACK；草稿/静音/定时任务各自独立。旧消息编辑/撤回仍仅原发送设备按现有时限执行。旧客户端不支持新授权链/信封时禁止开启多设备；未开启账号继续原单设备协议，密码登录不得成为隐式设备替换。

## 实现前门槛

两台 Windows 验证：两组公私钥证明、指纹核对、响应丢失、重放/过期、并发加入/撤销、错误根、授权链乱序/篡改、设备上限、旧客户端拒绝、撤销旧 HTTP/WS/refresh、离线撤销、新旧历史隔离、迁移中断/损坏和原发送设备编辑权限。

独立审查重点为授权根长期持有、设备目录回滚、收件集合/事务竞争，以及迁移正文与原证据的信任差异。审查和可运行验证通过前，不开放普通用户多设备登录。失去原设备但持有 T22 备份时只能离线阅读；在线根恢复必须另行设计。
