# D-03 消息操作规则与实现

2026-09-13：Windows 开发完成，待验收。本轮按用户要求跳过全部测试，编译/构建通过不代表实机或联调验收通过。客户端、Rust sidecar 与服务端统一升级；旧纯文本和原消息链继续读取。

## 用户行为

| 操作 | 行为 | 权限与限制 |
| --- | --- | --- |
| 复制 | 将当前显示的消息正文写入系统文本剪贴板 | 不读取剪贴板；撤回后不再提供正文复制 |
| 引用回复 | 保存原消息编号、来源名称与最多 500 字符的快照；可定位已加载原消息 | 快照与正文一同加密；不随原文编辑/撤回而改写 |
| 转发 | 选择联系人并生成加密草稿，再由用户点击发送 | 不覆盖目标已有草稿；来源由转发者提供，不等于原作者的签名证明 |
| 从本机删除 | 从当前账号的聊天、分页历史、摘要与未读计数中移除 | 逻辑删除；不通知对方、不取消投递，不释放原密文；确认前明确说明 |
| 编辑 | 更新双方显示的正文并保留“已编辑”和版本标记 | 仅原发送设备；服务端首次接收后的 48 小时内；保留原有引用/转发上下文 |
| 撤回 | 双方显示“此消息已被发送者撤回”，不再提供正文的回复/复制/转发入口 | 与编辑相同的身份/期限规则；撤回是最终状态，不能继续编辑 |

编辑/撤回期限以服务端记录的原消息接收时间和服务端当前时间为准。界面按本地时间做预判断，最终以服务端返回为准。原消息尚未存入服务端时不能操作。为保证权限可核对，当前不允许同账号另一台设备修改原发送设备的消息；跨设备身份与历史迁移仍属于 E-01。

撤回不等于安全擦除：对方此前查看、截图、复制、引用或转发的内容不会被远程销毁。原始加密记录保留用于完整性链与去重，变更记录也以密文保存。撤回占位仍是收到的消息，可以计入本机未读，打开加载后按 D-01 规则标记已读。本机已删除的消息不会因后续编辑或撤回重新出现。

## 完整流程

1. 桌面读取保存的身份、原消息与发件记录，确认原发送设备；从服务端查询原消息对应的仍有效收件设备。
2. 为每个收件设备及原发送设备生成加密变更副本。发送端的本机副本使用现有联系人密钥方案，以便历史恢复。
3. 为变更生成独立 UUID；签名绑定操作编号、目标消息、会话、发送者及设备、操作类型、基础版本、收件设备和密文。SQLite 保存密文请求后才发送 HTTP 请求。
4. 服务端校验会话与设备有效性、原发送者及设备、48 小时期限、每份签名及收件设备集合。对同一原消息加事务锁，检查基础版本后分配下一版本。
5. 服务端在一个事务内写入变更和全部设备的待投递记录。已接受的相同 UUID/内容重试返回原确认，超过期限后也不会把已经成功的操作错误地重新执行；同编号不同内容拒绝。
6. 桌面串行同步循环重试待确认发件操作，领取当前设备的变更。保存 SQLite 后才发送确认。确认失败或进程中断时可重复补收，不依赖容易漏掉并发提交的时间游标。
7. 展示历史时核对变更签名、原消息身份与消息链状态，再解密投影到界面。原消息尚未到达时保存变更，待原消息补到后重新读取应用。聊天加载前先读取本机变更，避免已撤回正文在重启时短暂闪现。

编辑每次使用完整替换正文，不依赖上一版正文到达。不同版本乱序到达时使用最高有效版本；有效撤回优先且不可逆。引用/转发仍保留创建时的快照。

## 错误与重试

- 网络失败、服务端暂时故障、限流或响应丢失：原密文请求保留为 pending，重连后自动重试同一个操作；界面也提供立即重试。
- 版本冲突、期限已过、权限失败、收件设备集合变化等明确拒绝：记录 rejected 与原因，原正文不变。用户同步后可重新发起符合规则的新操作。
- 有待确认操作时不允许为同一消息再创建另一个操作，避免把不确定的提交当作失败后重复操作。
- 签名无效、原消息身份不匹配、联系人密钥不可用或原消息完整性异常：不应用正文变更，展示原因；保存加密记录供之后核对。
- 编辑对话框未提交的文字仅在该对话框中保留；点击保存并完成本地密文写入后的操作可在重启后继续重试。普通聊天草稿仍按 D-02 加密持久化。
- 原始正文仍在本机逻辑删除标记之下保留。原始底层数据接口不等同于经过可见性及变更投影的 Windows 聊天界面。

## 存储与接口

- `shared/src/message_operation.rs`：跨端变更结构、48 小时常量及签名输入定义。
- PostgreSQL `message_operations`：原消息的追加变更、版本及幂等请求；`operation_deliveries`：每设备密文及确认标记。待投递记录不因设备离线自动删除；当前没有自动清理变更历史的策略。
- SQLite `local_message_operations`：按账号/设备保存 pending、accepted、rejected 密文及错误；不存编辑正文的明文。
- 原消息的发送者、会话、收件设备与服务端接收时间取自 `beta_receipts` 回执；收件确认后删除离线密文不影响变更。
- `GET /message-operations/targets/:id?device_id=...`：原发送设备查询原消息的有效收件设备。
- `POST /message-operations`：提交签名、加密的变更。
- `GET /message-operations?device_id=...`：领取最多 100 条未确认变更。
- `POST /message-operations/ack`：仅确认当前认证设备的最多 100 条记录。
- 桌面新增 `submit_message_operation`、`sync_message_operations`、`get_message_operations` 三个业务命令；总计 39 个 API，其中复制由 Electron 主进程处理，其余经 Rust sidecar。

编辑正文封装最多 64 KiB，每份密文最多 128 KiB，操作最多 100 份设备副本且总密文不超过 384 KiB。过大时提示缩短内容。常规文字发送的限制不由此条修改。
