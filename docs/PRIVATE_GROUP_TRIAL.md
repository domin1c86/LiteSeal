# 小型私密群设计与实现记录（T20）

## 当前交付和范围

`shared/src/group.rs` 已有纯状态转换、邀请/接受、签名验证、成员版本及群消息收件集合/链验证。以下命令只生成内存中的合成身份，不连接服务器、不读取本机账号或密钥文件：

```powershell
cargo run --locked -p liteseal-shared --example group_trial
cargo test --locked -p liteseal-shared --test group_trial_test
```

共享核心覆盖首轮 3～10 人的技术基础，服务端成员管理和邀请接口已接入源码；**群消息持久投递、桌面业务命令和 Windows 界面尚未接入**，不能从当前桌面产品创建或发送群消息。T20 保持部分实现，验收框未勾选。

## 成员和版本规则

- 每个账号沿用当前内测的单设备身份，包含用户编号、设备编号、加密公钥和独立签名公钥。创建时群主一人，最多 10 人；离开/移除后允许人数降至 1～2 人，一人群不发送聊天消息。
- 群主签名创建、改名、邀请、移除和关闭。普通成员只能签名退出自己。群主退出需显式关闭群；首轮没有群主转移和多级管理员。群名最多 160 UTF-8 字节，不接受控制字符。
- 邀请绑定当前群版本、前一变更哈希、目标账号/设备/公钥和期限，最长 7 天。邀请者签名后，目标成员还须签名接受，才能提交加入变更。任何版本变化使原邀请失效，需要重新邀请，不自动替换新公钥或扩张授权。
- 每次变更版本严格加一，并绑定前一签名变更的哈希。`GroupState` 无不受验证的反序列化入口，必须由已钉住的创建身份及有序签名事件重建；`pin_creation` 将创建者与独立核实的账号/设备记录比较，不能直接把服务端返回的自签身份当成信任锚。离线重放按事件签名中的加入时刻验证历史邀请，不能以今天的过期时间否定已接受的历史加入。
- 新提交同时校验服务端当前时钟与签名时刻（60 秒范围）以及邀请实际期限。客户端历史重放与服务端新提交使用不同入口；服务端不得把历史重放入口用于接受新的过期邀请。
- 每次加入都有独立 `joined_epoch`。退出后重新加入，即使账号和密钥不变，也使用新的加入版本；收发消息链按双方加入版本隔离，不能把旧加入阶段的队列或链直接接回新加入阶段。

## 消息、加密与历史

首轮文字上限 4096 UTF-8 字节。发送者对当前其他成员各生成一份密文；不下发共用的群解密密钥。每份信封由发送者签名，绑定群编号、成员版本及哈希、双方账号/设备/加入版本、消息编号、每收件设备的序号/前哈希、发送时刻和密文。服务端必须在同一事务中验证并接受完整收件集合，缺项、重复项、旧成员和非成员均不能混入。

继续使用现有 `crypto_box` 加密和独立 Ed25519 签名。公开密钥加密为指定收件人提供认证解密，作者签名用于独立验证完整信封。基础原语见 [Libsodium 认证加密](https://doc.libsodium.org/public-key_cryptography/authenticated_encryption)和[独立签名](https://doc.libsodium.org/public-key_cryptography/public-key_signatures)。

移除成员后，新版本不再为其生成密文；新加入成员没有加入前的收件密文。已有成员在本机保存的历史继续可读，退出/关闭不销毁历史。成员可以主动复制或外传自己已经读到的内容；本设计不承诺阻止这些行为。静态身份密钥沿用现有生命周期，当前没有逐消息前向保密或失密后的自动密钥恢复。

群名、成员、版本、路由、时间和大小对服务端可见。试验依赖服务端提供最新已提交的版本并执行权限过滤；签名链能检查已取得事件的身份、顺序和篡改，无法单独证明服务端没有隐藏更新或给不同客户端提供相互隔离的版本分支。这些边界需写入后续产品说明和安全审查。

## 第二阶段：服务端和持久队列（部分实现）

### 已接入源码：成员和邀请

PostgreSQL 迁移 9 新增群、签名事件、成员加入阶段及邀请表。创建/成员变更/邀请/撤销在群事务锁内执行；群版本、事件、成员投影和邀请接受一起提交。会话、设备与公钥在事务中核对，创建身份取注册记录作为信任锚。设备和会话锁保持到提交，等待上限 5 秒、单条语句上限 10 秒；同群操作先锁群，再锁设备/会话。此迁移与真实事务行为尚未在专用数据库运行。

| 接口 | 权限与返回 |
| --- | --- |
| `POST /groups` | 已登录设备提交自己的签名创建事件 |
| `GET /groups?device_id=…&after_id=…` | 该设备的当前/历史成员阶段；每页 100 群 |
| `POST /groups/:id/changes` | 注册设备与当前成员身份一致；加入还需存储中的有效邀请及目标双签名 |
| `GET /groups/:id/changes?device_id=…&after_epoch=…` | 当前成员到最新版本；已退出成员截断于最后退出/移除版本；有效目标邀请可提供当前签名链；每页 100 事件 |
| `POST /groups/:id/invites` | 当前群主；目标未撤销设备及冻结公钥匹配，双方未拉黑/拒绝 |
| `GET /group-invites?device_id=…&after_id=…` | 仅该设备有效、未过期、当前版本的目标邀请；每页 100 项 |
| `DELETE /group-invites/:id?device_id=…` | 原目标设备拒绝或原群主设备撤销；已接受邀请不能撤销 |

重复提交只在内容与已保存记录完全相同时返回原结果；相同版本不同内容为 409。邀请被版本变化、关闭、拒绝或撤销后不能新加入。邀请拒绝/撤销是认证会话下的服务端状态，不是客户端可独立验证的签名群事件，仍依赖服务端正确执行。群列表和事件接口不提供聊天密文。

试验限额：每人 20 个未关闭的自建群、100 个当前成员关系、100 个有效目标邀请；每群保留最多 2000 个邀请、1000 个普通成员版本并预留第 1001 个版本关闭；成员操作每账号每分钟 40 次。成员/邀请请求体上限 32 KiB。超限明确拒绝，现阶段没有历史清理或自动扩容。

后续步骤和已实现项的验收要求：

1. **成员存储与原子版本检查。** 新表保存群当前版本、签名事件、成员加入/移除版本和邀请。提交时锁群记录，核对账号令牌和未撤销设备；签名身份及公钥须与服务端注册记录一致。调用 `validate_submission`，版本及哈希比较后一起更新事件和成员投影。重复请求复用已接受内容，编号相同但内容不同则拒绝。并发变更只接受一个版本，失败方须获取新版本后重试。
2. **邀请权限。** 邀请只向明确目标的有效会话开放。受邀者可取得验证邀请所需的签名成员链和群资料；邀请本身不授予聊天密文访问。对邀请数量、期限和提交频率设限。
3. **离线移除通知。** 当前成员取得后续有序事件；被移除者仍须能取得自己的最后移除事件和此前授权的成员链，不能因为最终成员表已删除该用户而让其永久停在旧版本。对其权限截断在移除版本，不返回之后的群变化。
4. **消息原子扇出。** 独立群接口复用已验证的当前状态，验证完整批次及每收件加入阶段的链位置。一个消息的全部收件密文/持久收据同事务提交，ACK 后保留幂等和链证据。旧版本发送明确失败，不能根据旧收件列表静默漏发或继续投递给已移除者。
5. **下载和补收。** 只提供当前有效成员对应当前加入阶段的收件密文。移除时停止正常补收旧待发队列，保留必要收据供审查；重新加入不能恢复旧队列。客户端先重放并验证对应成员版本，再验签、认证解密、验证链和落库，最后 ACK。不同成员不共享 ACK 或已读状态。
6. **尺寸和兼容。** 群批次最多 9 个收件密文，独立 REST 上传上限拟为 512 KiB，不塞入当前 64 KiB WebSocket 消息限制。新群事件需能力声明或独立增量接口，避免把未知消息发送给旧客户端；原单聊协议保持原义。所有限额须按实际编码验证后再接入。

## 第三阶段：Windows 产品接入（尚未实现）

Rust 保管密钥、签名变更并保存加密发件任务；渲染进程取得公开成员资料和解密后正文。群会话使用独立 `group:<id>` 存储标识，不能误用双人会话路由或直接复制单聊操作权限。

界面需提供创建群、明确邀请目标及指纹、接受/拒绝、群主改名/移除/关闭、普通成员退出、当前成员和版本、文字发送及失败重试、重启历史与离线更新。T21 的提及、置顶、投票另行接入；单聊附件、回应、阅读回执、输入提示、定时发送目前不自动成为群功能。

## 本轮可证明的内容与仍未覆盖场景

8 项共享核心自动化覆盖：有序历史重放、邀请双签名、群主/成员权限、移除后的密文隔离、新成员历史隔离、完整收件集合、重新加入的独立链、签名字段绑定、成员上限和输入约束。示例中实际执行加密、验签和解密失败断言。另有 2 项无需数据库的访问截断用例及扩展的 HTTP 鉴权路由回归。

新增 2 项专用 PostgreSQL 用例（已编译、未执行）：邀请目标与接受签名、伪造提交不改版本、幂等提交、移除后只见最后事件；并发同版本只接受一个、邀请撤销、关闭后目标无权限及成员投影一致。设置隔离测试库后运行 `cargo test --locked -p liteseal-server group_tests -- --ignored`；勿使用开发或用户数据所在数据库。

当前通过的证据属于共享核心、合成身份及无数据库路由验证，尚不能证明真实群接口拒绝非成员、数据库事务故障可恢复、真实离线成员一致或 Windows 多客户端可用。后续仍需专用 PostgreSQL、3～10 个隔离账号、多客户端及独立协议安全审查；没有这些结果前不勾选 T20。
