# 小型私密群设计与实现记录（T20）

## 当前交付和范围

`shared/src/group.rs` 已有纯状态转换、邀请/接受、签名验证、成员版本及群消息收件集合/链验证。以下命令只生成内存中的合成身份，不连接服务器、不读取本机账号或密钥文件：

```powershell
cargo run --locked -p liteseal-shared --example group_trial
cargo test --locked -p liteseal-shared --test group_trial_test
```

共享核心、服务端成员/消息、Rust 客户端和 Windows 基础文字群界面现已接入源码。可从桌面“群聊”入口使用创建、明确指纹核实、邀请、成员管理和文字收发；证据来自同机隔离双进程及模拟界面，**真实数据库、双机和 3～10 人场景未验收**。T20 保持部分实现，验收框未勾选。规则见[群客户端核心](GROUP_CLIENT_CORE.md)及[Windows 群聊说明](WINDOWS_GROUPS.md)。

## 成员和版本规则

- 每个账号沿用当前内测的单设备身份，包含用户编号、设备编号、加密公钥和独立签名公钥。创建时群主一人，最多 10 人；离开/移除后允许人数降至 1～2 人，一人群不发送聊天消息。
- 群主签名创建、改名、邀请、移除和关闭。普通成员只能签名退出自己。群主退出需显式关闭群；首轮没有群主转移和多级管理员。群名最多 160 UTF-8 字节，不接受控制字符。
- 邀请绑定当前群版本、前一变更哈希、目标账号/设备/公钥和期限，最长 7 天。邀请者签名后，目标成员还须签名接受，才能提交加入变更。任何版本变化使原邀请失效，需要重新邀请，不自动替换新公钥或扩张授权。
- 每次变更版本严格加一，并绑定前一签名变更的哈希。`GroupState` 无不受验证的反序列化入口，必须由已钉住的创建身份及有序签名事件重建；`pin_creation` 将创建者与独立核实的账号/设备记录比较，不能直接把服务端返回的自签身份当成信任锚。离线重放按事件签名中的加入时刻验证历史邀请，不能以今天的过期时间否定已接受的历史加入。
- 新提交同时校验服务端当前时钟与签名时刻（60 秒范围）以及邀请实际期限。客户端历史重放与服务端新提交使用不同入口；服务端不得把历史重放入口用于接受新的过期邀请。
- 每次加入都有独立 `joined_epoch`。退出后重新加入，即使账号和密钥不变，也使用新的加入版本；收发消息链按双方加入版本隔离，不能把旧加入阶段的队列或链直接接回新加入阶段。

## 消息、加密与历史

首轮文字上限 4096 UTF-8 字节。发送者对当前其他成员各生成一份密文；不下发共用的群解密密钥。每份信封由发送者签名，绑定群编号、成员版本及哈希、双方账号/设备/加入版本、消息编号、每收件设备的序号/前哈希、发送时刻和密文。服务端必须在同一事务中验证并接受完整收件集合，缺项、重复项、旧成员和非成员均不能混入。

继续使用现有 `crypto_box` 加密和独立 Ed25519 签名。公开密钥加密为指定收件人提供认证解密，作者签名用于独立验证完整信封。基础原语见 [Libsodium 认证加密](https://doc.libsodium.org/public-key_cryptography/authenticated_encryption)和[独立签名](https://doc.libsodium.org/public-key_cryptography/public-key_signatures)。

移除成员后，新版本不再为其生成密文；新加入成员没有加入前的收件密文。已有成员在本机保存的历史继续可读，退出/关闭不销毁历史。成员可以主动复制或外传自己已经读到的内容；本设计不承诺阻止这些行为。静态身份密钥沿用现有生命周期，当前没有逐消息前向保密或失密后的自动密钥恢复。

群名、成员、版本、路由、时间和大小对服务端可见。试验依赖服务端提供最新已提交的版本并执行权限过滤；签名链能检查已取得事件的身份、顺序和篡改，无法单独证明服务端没有隐藏更新或给不同客户端提供相互隔离的版本分支。这些边界需写入后续产品说明和安全审查。

## 第二阶段：服务端和持久队列（部分实现）

### 已接入源码：成员和邀请

PostgreSQL 迁移 9 新增群、签名事件、成员加入阶段及邀请表。创建/成员变更/邀请/撤销在群事务锁内执行；群版本、事件、成员投影和邀请接受一起提交。会话、设备与公钥在事务中核对，创建身份取注册记录作为信任锚。设备和会话锁保持到提交，等待上限 5 秒、单条语句上限 10 秒；同群操作先锁群，再锁设备/会话。此迁移与真实事务行为尚未在专用数据库运行。

| 接口 | 权限与返回 |
| --- | --- |
| `POST /groups` | 已登录设备提交自己的签名创建事件 |
| `GET /groups?device_id=…&after_id=…` | 该设备的当前/历史成员阶段；每页 100 群 |
| `POST /groups/:id/changes` | 注册设备与当前成员身份一致；加入还需存储中的有效邀请及目标双签名 |
| `GET /groups/:id/changes?device_id=…&after_epoch=…` | 当前成员到最新版本；已退出成员截断于最后退出/移除版本；有效目标邀请可提供当前签名链；每页 100 事件 |
| `POST /groups/:id/invites` | 当前群主；目标未撤销设备及冻结公钥匹配，双方未拉黑/拒绝 |
| `GET /group-invites?device_id=…&after_id=…` | 仅该设备有效、未过期、当前版本的目标邀请；每页 100 项 |
| `DELETE /group-invites/:id?device_id=…` | 原目标设备拒绝或原群主设备撤销；已接受邀请不能撤销 |

重复提交只在内容与已保存记录完全相同时返回原结果；相同版本不同内容为 409。邀请被版本变化、关闭、拒绝或撤销后不能新加入。邀请拒绝/撤销是认证会话下的服务端状态，不是客户端可独立验证的签名群事件，仍依赖服务端正确执行。群列表和事件接口不提供聊天密文。

试验限额：每人 20 个未关闭的自建群、100 个当前成员关系、100 个有效目标邀请；每群保留最多 2000 个邀请、1000 个普通成员版本并预留第 1001 个版本关闭；成员操作每账号每分钟 40 次。成员/邀请请求体上限 32 KiB。超限明确拒绝，现阶段没有历史清理或自动扩容。

### 已接入源码：群消息持久投递

迁移 10 新增消息批次、逐收件人持久收据和待收密文。新消息先锁群、核对认证发送者和全部未撤销成员设备，再验证完整收件集合、当前签名成员版本、实际提交时刻（60 秒范围）和每对加入阶段的链位置，全部收据/密文在同一事务中提交。成员变更与消息投递共享群事务锁，旧版本未入库消息明确拒绝。每对收发设备和加入阶段的序号有数据库唯一约束，不能并发接受两个相同链位置。

| 接口 | 权限与返回 |
| --- | --- |
| `POST /groups/:id/messages` | 认证发送设备提交 `GroupSendRequest` 完整批次，返回逐收件人持久状态 |
| `GET /groups/:id/messages?device_id=…` | 当前有效成员的当前加入阶段待收窗口；最多 100 份信封、完整 JSON 响应不超过 512 KiB；未 ACK 的窗口会重发 |
| `POST /groups/:id/messages/ack` | 当前收件设备及加入版本，1～100 个不重复消息编号；全量权限检查后原子 ACK，允许重复 ACK |
| `GET /groups/:id/messages/:message_id/receipt?device_id=…` | 只向原发送设备返回该批次的收件状态；退出或关闭后仍可核对自己的原发送记录 |

批次按收件设备排序计算带独立域的 SHA-256 摘要，收件数组重排不改变幂等结果。相同群消息编号只有原发送者及完全相同批次可复用，改变密文或签名即拒绝。原批次已接受时，重试即使在成员变化或关闭后也只返回原收据，不重新排队；新的旧版本批次仍拒绝。

ACK 状态为 `delivered`，只表示该收件客户端确认处理完成，不表示可见已读。该收件人的待收密文删除，其他人的队列不变；保留批次摘要、路由、签名及 `GroupChainHead`（链哈希/序号/双方加入版本等公开元数据），继续检查后续消息链。链头必须来自本地已验证信封或服务端已接受记录，不是新的远端信任入口。离开/移除/关闭在同一成员事务中删除相应加入阶段的待收密文，未完成收据变为 `removed`；已完成收据保留 `delivered`。重新加入只取得新的加入阶段队列，不能重新 ACK 或下载旧阶段内容。

任何发送者与收件成员之间存在拉黑/拒绝时，整批新发送拒绝，避免少发一个成员破坏完整收件集合。下载时也过滤双方拉黑/拒绝的发送者；队列暂时保留并计入配额，解除策略后可以补收。此规则意味着群内存在这类策略时，发送者需处理成员关系或策略后才能发送。

实际限制：每批最多 9 个收件密文、每份密文最多 4136 字节，上传 JSON 上限 512 KiB；每设备跨群待收最多 1000 份或 10 MiB（按存储 JSON UTF-8 字节计），每群最多 10000 个保留批次及取消记录合计，发送每账号每分钟 120 次。超队列/保留上限返回 507，限频为 429，版本/签名/链冲突为 409。ACK 和移除只减少队列；新发送按稳定设备顺序加跨群配额锁。群接口采用独立 REST 增量窗口，不向旧单聊 WebSocket 发送未知类型；原单聊协议未改变。

### 已接入源码：发件原子取消

迁移 11 和 `POST /groups/:id/messages/:message_id/cancel` 将取消与新投递放在同一群事务锁下。已入库原消息只向原发送设备返回原收据，不撤回或删除已经授权的收件密文；未入库时，具有当前/历史成员关系的认证设备为自己的消息编号保存取消标记，迟到的原请求和后续同编号新提交被拒绝。已关闭群未入库消息无需新增标记，因为关闭本身持续拒绝新提交。重复取消返回同一结论，标记不影响其他发送设备的编号权限。

客户端不能仅以一次“查不到收据”认定发送失败，也不会在用户点击取消时重新提交正文。只有原子取消结果确认成功才清除本机待发状态；若返回原收据，则按已接受处理并提示不能取消。网络错误保留原任务和原密文。取消调用沿用成员操作每分钟 40 次限制，记录与批次共同计入保留上限；真实并发结果仍待专用数据库验收。

这些是源码规则，迁移 10 和真实事务行为仍待专用数据库执行。服务端无法证明客户端确实验签解密及落库，后续客户端必须在完成这些步骤后才 ACK。

后续客户端步骤和已实现项的验收要求：

1. **成员存储与原子版本检查。** 新表保存群当前版本、签名事件、成员加入/移除版本和邀请。提交时锁群记录，核对账号令牌和未撤销设备；签名身份及公钥须与服务端注册记录一致。调用 `validate_submission`，版本及哈希比较后一起更新事件和成员投影。重复请求复用已接受内容，编号相同但内容不同则拒绝。并发变更只接受一个版本，失败方须获取新版本后重试。
2. **邀请权限。** 邀请只向明确目标的有效会话开放。受邀者可取得验证邀请所需的签名成员链和群资料；邀请本身不授予聊天密文访问。对邀请数量、期限和提交频率设限。
3. **离线移除通知。** 当前成员取得后续有序事件；被移除者仍须能取得自己的最后移除事件和此前授权的成员链，不能因为最终成员表已删除该用户而让其永久停在旧版本。对其权限截断在移除版本，不返回之后的群变化。
4. **消息原子扇出。** 独立群接口复用已验证的当前状态，验证完整批次及每收件加入阶段的链位置。一个消息的全部收件密文/持久收据同事务提交，ACK 后保留幂等和链证据。旧版本发送明确失败，不能根据旧收件列表静默漏发或继续投递给已移除者。
5. **下载和补收。** 只提供当前有效成员对应当前加入阶段的收件密文。移除时停止正常补收旧待发队列，保留必要收据供审查；重新加入不能恢复旧队列。客户端先重放并验证对应成员版本，再验签、认证解密、验证链和落库，最后 ACK。不同成员不共享 ACK 或已读状态。
6. **尺寸和兼容。** 群批次最多 9 个收件密文，独立 REST 上传上限已为 512 KiB，不塞入当前 64 KiB WebSocket 消息限制。当前使用独立增量接口，避免把未知消息发送给旧客户端；原单聊协议保持原义。上传限额已有无数据库 HTTP 回归；下载窗口和配额仍须真实数据库验收。

## 第三阶段：客户端与 Windows 产品（部分实现）

`core/src/groups/` 已接入 REST、钉住创建者的签名成员链同步、群主/成员操作、邀请双签名、加密发件任务和原批次重试、验证解密后原子落库、重启 ACK 补交及本机历史分页。正文及草稿使用身份密钥的认证密文保存，范围绑定服务器/账号/设备/公钥及群/消息编号。桌面已接入会话缓存、16 个业务命令、主进程后台补收和群界面，真实 PostgreSQL 尚未运行。详见[群客户端核心](GROUP_CLIENT_CORE.md)及[Windows 群聊说明](WINDOWS_GROUPS.md)。

Rust 保管密钥、签名变更并保存加密发件任务；渲染进程取得公开成员资料和解密后正文。群会话使用独立 `group:<id>` 存储标识，不能误用双人会话路由或直接复制单聊操作权限。

界面已提供创建群、明确邀请目标及两组公钥指纹、接受/拒绝、核实恢复、群主改名/移除/关闭、普通成员退出、当前成员、文字发送及失败重试/取消、历史分页及加密草稿。主进程每 10 秒轮转补收，锁定时不向页面发送结果，长时间/多群延迟仍须实测。T21 的提及、置顶、投票另行接入；单聊附件、回应、可见阅读回执、输入提示、定时发送目前不自动成为群功能。群原生通知点击路由、已发邀请管理及群数据统计/清理仍待补齐。

## 本轮可证明的内容与仍未覆盖场景

9 项共享核心自动化覆盖：有序历史重放、邀请双签名、群主/成员权限、移除后的密文隔离、新成员历史隔离、完整收件集合、重新加入的独立链、签名字段绑定、成员上限和输入约束，以及 ACK 后无密文的链证据。示例中实际执行加密、验签和解密失败断言。另有 2 项无需数据库的访问截断用例、3 项队列/ACK/批次摘要边界用例，以及扩展的 HTTP 鉴权和独立上传限额回归。

5 项专用 PostgreSQL 群用例（已编译、未执行）：邀请目标与接受签名、伪造提交不改版本、幂等提交、移除后只见最后事件；并发同版本只接受一个、邀请撤销、关闭后目标无权限及成员投影一致；完整原子扇出、独立/重复 ACK、新成员无旧队列、移除/关闭清队列及重新加入链隔离；配额拒绝不改变其他人队列、并发消息链只接受一个、拉黑和撤销设备拒绝投递；取消与入库竞争、取消后迟到提交拒绝、已接受消息不被取消。设置隔离测试库后运行 `cargo test --locked -p liteseal-server group_tests -- --ignored`；勿使用开发或用户数据所在数据库。

客户端另有 9 项通过的隔离回归，包含加密发件重启、收据身份绑定、服务器/设备范围隔离、错误私钥拒绝、无效消息不 ACK、故障事务回滚、成员链分支拒绝、重新加入隔离、模拟 REST 下的重启 ACK 和超时发送重试、原子取消结果处理、历史分页及密文复制检测。

本轮另通过同机两个隔离 Rust 桌面进程的双签名加入、实际加密/验签/解密、ACK、草稿、令牌刷新及本机读取不等待网络；Playwright 在模拟桌面接口中验证 1280×900 和 390×844 界面交互、焦点、未读、历史及失败重试，控制台无错误。尚不能证明真实群 SQL 权限、数据库故障恢复、真实离线一致或双机可用。后续仍需专用 PostgreSQL、3～10 个隔离账号、多客户端及独立协议安全审查；没有这些结果前不勾选 T20。
